Operação · sem terminal

Deploy em outro workspace

Guia 100% via interface do Databricks (Workspace Browser, Apps, Catalog Explorer, SQL Editor). Nenhum comando CLI, nenhum git local. Pega o código pela UI do workspace origem, importa no destino, edita 1 arquivo, clica Deploy.

Visão geral em 1 minuto

  1. No workspace origem: exporta a pasta do código como .zip (Workspace Browser → Export).
  2. No workspace destino: importa o .zip na sua home (Workspace Browser → Import).
  3. Edita apenas 1 arquivo: app.yml. Quatro placeholders.
  4. Cria o app, copia o Application ID do Service Principal, dá os grants no Catalog UI.
  5. Clica Deploy. O Databricks faz build, roda migrations (cria as 22 tabelas Delta) e sobe o uvicorn.
  6. Acessa a URL do app, faz bootstrap do primeiro ADMIN via SQL Editor.
Nada local Sem Python, Node, git push, ou Databricks CLI. Tudo browser. Build da UI (Vite) e instalação Python (uv) rodam dentro do container do Databricks Apps no momento do deploy.

2. Exportar código do workspace origem

O código já está sincronizado num path tipo /Workspace/Users/<email-deployer>/nuclea-modeler no workspace origem.

  1. Faça login no workspace origem

    URL do workspace onde o app está rodando hoje.

  2. Abra a pasta do código

    Menu lateral: Workspace
    Navegue até Users › <email-deployer> › nuclea-modeler

  3. Exporte como .zip

    Clique no ⋮ ao lado do nome da pasta nuclea-modeler
    Selecione Export → Source File (.zip)
    O browser baixa nuclea-modeler.zip contendo todo o código.
    Importante · escolha "Source File", NÃO "DBC" DBC empacota só notebooks e perde arquivos não-notebook (.py, .ts, .json). Source File (.zip) preserva todos os bytes como estão.

  4. (Opcional) Exporte também os dados

    Só se quiser migrar os dados existentes (modelos, tickets, etc), não só começar limpo.
    No SQL › SQL Editor do workspace origem, rode:
    -- Substitua origem e destino
CREATE TABLE CATALOG_DESTINO.SCHEMA_DESTINO.systems
  DEEP CLONE CATALOG_ORIGEM.SCHEMA_ORIGEM.systems;
-- Repita pras 22 tabelas (lista no passo 8.4)
    Alternativa: Delta Sharing entre os 2 workspaces se eles compartilham metastore.

3. Importar no workspace destino

  1. Faça login no workspace destino

    URL diferente do origem. Use sua conta com permissão de admin/can-manage-apps.

  2. Crie a pasta na sua home

    Workspace › Users › <seu-email>
    No ⋮, escolha Create → Folder
    Nome: nuclea-modeler

  3. Importe o .zip

    Entre na pasta nuclea-modeler que acabou de criar.
    No ⋮ da pasta vazia, escolha Import
    Selecione o arquivo nuclea-modeler.zip baixado.
    No diálogo, escolha o tipo "Source files". Confirme.
    A UI mostra um spinner. Depois alguns segundos a pasta exibe toda a árvore.
    Limite de upload Workspace Import aceita até ~10MB por zip. O Núclea Modeler descompactado tem <5MB, sem problemas. Se exceder por algum motivo, exporte em subpastas separadas (src.zip, databricks.zip, etc) e importe sequencialmente.

  4. Confirme a estrutura

    Você deve ver dentro da pasta importada:
    • app.yml ← esse é o único que você vai editar
    • app.yml.example (template de referência)
    • requirements.txt, pyproject.toml, package.json
    • databricks/sql/001_create_schema.sql até 012_indexes_and_partitioning.sql
    • src/nuclea_modeler/backend/app.py
    • scripts/run_migrations.py

4. Arquivos a editar

Apenas 1 arquivo Só o app.yml. Todo o resto (migrations, código, deps) é parametrizado via env vars dentro desse YAML.

Lista completa de arquivos que mudam

ArquivoStatusO que muda
app.yml obrigatório 4 placeholders: Warehouse ID (2x), Catalog name, Lakebase instance (opcional)
app.yml.example referência Não muda — é o template original
databricks/sql/*.sql auto SQLs usam ${CATALOG}/${SCHEMA} que o runner resolve via env vars. Não toque.
requirements.txt auto Não toca. uv instala no container do app.
package.json auto Não toca. vite build dispara no container.
databricks/dashboards/*.json opcional Só se for instalar o Lakeview Dashboard — substituir 1 placeholder de catalog (passo 8.6)

Editando o app.yml

  1. Abra o arquivo no editor da Workspace

    Na pasta importada (passo 3), duplo-clique em app.yml.
    A Workspace abre o arquivo num editor de texto inline (sem precisar download/upload).
    Dica · começar do zero Se quiser começar do template limpo: copie todo o conteúdo de app.yml.example e cole sobrescrevendo app.yml. O .example tem comentários explicativos ao lado de cada placeholder.

  2. Substitua os 4 placeholders

    Procure por <WAREHOUSE_ID>, <CATALOG_NAME>, <LAKEBASE_INSTANCE_NAME> e substitua pelos valores que anotou no passo 1.

    Estado final esperado:

    app.yml
    command:
  - sh
  - -c
  - >
    set -e;
    cd /app/python/source_code;
    echo '[NUCLEA] Building UI...';
    if [ -f node_modules/.bin/vite ]; then
      ./node_modules/.bin/vite build || echo '[NUCLEA] UI build failed';
    fi;
    echo '[NUCLEA] Running migrations...';
    PYTHONPATH=src python -m scripts.run_migrations || exit 1;
    echo '[NUCLEA] Starting uvicorn...';
    exec uvicorn nuclea_modeler.backend.app:app \
      --host 0.0.0.0 --port 8000 --workers 2 --app-dir src

resources:
  - name: nuclea-warehouse
    description: SQL Warehouse para tabelas Delta do app
    sql_warehouse:
      id: "abc123def"            ## ← Warehouse ID anotado
      permission: CAN_USE

  # ↓ Bloco abaixo é OPCIONAL. Remova/comente se NÃO usar Lakebase.
  - name: nuclea-lakebase
    description: Lakebase Postgres para validação dos modelos
    database:
      database_name: "databricks_postgres"
      instance_name: "JDBCTESTLAKEBASE"  ## ← Lakebase instance
      permission: CAN_CONNECT_AND_CREATE

env:
  - name: PYTHONPATH
    value: /app/python/source_code/src
  - name: NODE_OPTIONS
    value: --max-old-space-size=2048

  # Catalog onde o app armazena estado (cria schema automaticamente)
  - name: NUCLEA_CATALOG
    value: "main"                ## ← seu Catalog name
  - name: NUCLEA_SCHEMA
    value: "nuclea_modeler"           ## deixa este, é criado automaticamente

  # Mesmo Warehouse ID declarado em resources (acima)
  - name: NUCLEA_WAREHOUSE_ID
    value: "abc123def"            ## ← idêntico ao resources
  - name: DATABRICKS_SQL_WAREHOUSE_ID
    value: "abc123def"            ## ← idêntico

  # Secret scope (criado opcionalmente no passo 7 — só pra ODBC/REST)
  - name: NUCLEA_SECRETS_SCOPE
    value: "nuclea-modeler"

  # Migrations rodam no `command:` (single-shot) — não deixar auto
  - name: NUCLEA_MIGRATIONS_AUTO_APPLY
    value: "false"

  # Logging
  - name: NUCLEA_LOG_JSON
    value: "true"
  - name: NUCLEA_LOG_LEVEL
    value: "INFO"
    SE NÃO USAR LAKEBASE Remova ou comente todo o bloco - name: nuclea-lakebase em resources:. Senão o app sobe mas falha em chamadas que tentam usar OAuth M2M com escopo postgres.

  3. Salve o arquivo

    Pressione Ctrl+S (Windows/Linux) ou ⌘+S (Mac).
    A Workspace persiste imediatamente. Sem git commit, sem push.

5. Criar o app pela UI

  1. Abra Apps

    Menu lateral: Compute › Apps

  2. Crie novo app

    Botão Create app no canto superior direito
    Campo Name: nuclea-modeler
    Campo Description: livre (ex: "Núclea data catalog & modeling")
    Confirme

  3. Copie o Application ID do Service Principal

    Na tela do app criado, vá em Service Principal (aba ou seção)
    Copie o Application ID (UUID tipo 11111111-2222-3333-4444-555555555555)
    Anote — vai usar nos grants do próximo passo.
    Por que esse ID? O app autentica no Unity Catalog / Lakebase como esse Service Principal. Todos os grants precisam ser feitos pra esse UUID, não pro seu usuário.

6. Conceder grants ao Service Principal

  1. Abra o Catalog Explorer

    Catalog
    Clique no catalog escolhido (ex: main)

  2. Acesse Permissions

    Aba Permissions no topo
    Botão Grant

  3. Cole o Application ID

    Campo Principals: cole o UUID copiado no passo 5
    Marque os checkboxes:
    • USE_CATALOG
    • USE_SCHEMA (se já existir um schema)
    • CREATE_SCHEMA
    • CREATE_TABLE
    • MODIFY
    • SELECT
    Confirme com Grant
    Atalho via SQL Editor Equivalente — se preferir, abra SQL › SQL Editor e rode: 
    GRANT USE CATALOG, CREATE SCHEMA, CREATE TABLE, MODIFY, SELECT
  ON CATALOG main
  TO `SEU_APPLICATION_ID`;

  4. (Se usar Lakebase) Grant na instance

    Compute › Lakebase → clique na instance
    Aba Permissions → adicione o Application ID com permissão Can Connect and Create

7. Deploy

  1. Configure o source code path

    Volte em Compute › Apps › nuclea-modeler
    Aba Settings (ou "App configuration")
    No campo Source code path: cole o caminho onde você importou no passo 3:
    /Workspace/Users/seu-email@cliente.com/nuclea-modeler
    Salve

  2. (Opcional) Crie secret scope

    Só se vai usar conexões ODBC ou REST a sistemas externos.
    Atualmente o Workspace UI não tem editor de secret scope pleno — crie via Admin Settings se disponível, ou peça pro admin Databricks rodar databricks secrets create-scope nuclea-modeler no terminal dele.
    Pra primeiro deploy, pode pular.

  3. Clique Deploy

    No header do app, botão Deploy
    Status passa por Provisioning → Starting → Running em ~1-2 min.
    Durante o deploy o container roda 3 etapas:
    1. vite build — gera o bundle React em src/nuclea_modeler/__dist__/
    2. python -m scripts.run_migrations — aplica as 12 migrations SQL em ordem (cria schema, tabelas, seeds)
    3. uvicorn — sobe o servidor FastAPI (2 workers, porta 8000)

9. Bootstrap do primeiro admin

O primeiro usuário que acessa fica como VIEWER por default. Pra ter ADMIN e poder aprovar tickets, gerenciar conexões, etc:

  1. Abra o SQL Editor do workspace destino

    SQL › SQL Editor

  2. Cole e rode

    INSERT INTO CATALOG_NAME.nuclea_modeler.user_roles
  (role_id, user_email, role_name, granted_at, granted_by)
VALUES (
  uuid(),
  'seu-email@cliente.com',
  'ADMIN',
  current_timestamp(),
  'bootstrap'
);

  3. Recarregue o app

    Volte na URL do app e faça reload. Agora você tem acesso completo: criar sistemas, fazer reverse engineering, aprovar tickets, gerar DDL, gerenciar RBAC.

    Arquivo: nuclea_modeler_dashboard.json

  2. Edite o JSON

    Duplo-clique no JSON, busque stable_classic_pg4xe1_catalog.data_catalog_app
    Substitua por <seu_catalog>.nuclea_modeler
    Salve

  3. Importe no Lakeview

    Selecione o JSON editado.
    Confirme. Dashboard sobe com 7 tiles de KPI.

10. Atualizações de versão

Quando a equipe Núclea Modeler publicar uma nova versão (você recebe um novo .zip):

  1. Backup do app.yml atual

    No ⋮ do arquivo app.yml na sua pasta → Export → salve uma cópia local.
    Por que esse backup O Import seguinte vai sobrescrever app.yml com o template novo (placeholders sem valores). Backup garante que você consegue reaplicar seus valores rapidamente.

  2. Re-import sobrescrevendo

    Na pasta nuclea-modeler, ⋮ → Import
    Selecione o zip novo. Aceite "Overwrite existing files".

  3. Re-edite app.yml

    Abra app.yml e cole novamente seus valores (Warehouse ID, Catalog, Lakebase) — ou compare com o backup.

  4. Deploy

    No app: Deploy
    Migrations novas (ex: 013_*.sql) aplicam automaticamente. Migrations já aplicadas ficam como skipped via checksum.

? Troubleshooting

Sintoma nos LogsCausaFix via UI
SCHEMA_NOT_FOUND SP do app sem CREATE SCHEMA no catalog Volte ao passo 6.3 — Catalog UI → Permissions → Grant CREATE_SCHEMA pro Application ID
required scopes: postgres Bloco nuclea-lakebase não declarado em resources: do app.yml Edite app.yml pela UI (passo 4) + Deploy
DRIFT detected: 0XX_*.sql SQL já aplicado teve hash mudado Normal em upgrades — app continua subindo. Investigue só se for migration sua
DER vazio / Dashboard sem dados Seeds (003-004-009) falharam Logs do app — procure stack trace nas migrations. Geralmente é grant ou catalog inválido
401 em todos os endpoints SSO força auth, browser sem cookie Abra a URL do app na mesma sessão que está logado no workspace
App fica em "Starting" infinito Container OOM (build pesado) Logs do app. Se OOM, aumente memory na Settings › Resource size
Bundle UI antigo após deploy Browser cache Hard refresh: ⌘+Shift+R (Mac) ou Ctrl+Shift+R (Win/Linux)
Coverage gate falhando em CI Ajuste de testes pendente Não afeta o app rodando — só o CI no GitHub. Equipe da Núclea ajusta
Pronto Se chegou aqui com logs verdes, 22 tabelas no Catalog Explorer e o app acessível via URL, o deploy está concluído. Estado migrado, app rodando independente do workspace origem.
