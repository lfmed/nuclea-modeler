Núclea Modeler

Catálogo & modelagem de dados corporativo — Databricks App nativo · v0.2.1 · commit 752b9be · analisado em 2026-06-08.

1. Visão Geral (Macro) e Objetivo do Projeto

O Núclea Modeler é um catálogo + ferramenta de modelagem de dados corporativos, entregue como um Databricks App nativo (full-stack FastAPI + React). Resolve o problema clássico de empresas com vários ambientes (HINT/HEXT/PROD), múltiplos SGBDs (Oracle, SQL Server, PostgreSQL, Databricks/Delta) e modelos lógicos em ferramentas externas (Embarcadero ER/Studio): consolida tudo num único lugar, versionado no Unity Catalog, com governança via tickets de aprovação.

O fluxo de valor principal é o ciclo engenharia reversa → modelagem → DDL. Um steward conecta o app a uma fonte (Lakebase Postgres, Unity Catalog, arquivo .DM1 ou SQL bruto) ou cria do zero; o app extrai entities, attributes, PKs, FKs, índices e particionamento, abre um ticket de reconciliação com o diff vs catálogo. Um architect/admin revisa, aprova — o app materializa as mudanças nas próprias tabelas Delta do Unity Catalog (sem tocar a fonte). Modeladores então editam o DER, atributos, relationships, índices — toda mutação vai pra um ticket OPEN editorial (janela de 15 minutos) que é aplicado em lote. Architects geram DDL multi-dialeto ou publicam versões snapshot.

Não há banco operacional externo — todo estado vive em 22 tabelas Delta dentro de ${CATALOG}.${SCHEMA} parametrizáveis. Isso torna o app workspace-agnostic (mesmo binário roda em qualquer Databricks com Unity Catalog) e o backup vira DEEP CLONE ou Delta TimeTravel.

Justificativa arquitetural

  • Databricks-native by design: distribuição via databricks apps, auth=SSO, estado=Delta no UC. Sem Postgres/Redis/S3 fora do workspace — reduz custo de operação a zero infra nova.
  • FastAPI + Pydantic v2: APIs tipadas com OpenAPI gerado; cliente TS sincronizado a partir do schema. Reduz drift back↔front.
  • TanStack Router + Suspense queries: routing file-based + reads sempre via useXSuspense + selector() com Suspense + ErrorBoundary. Pattern uniforme em toda UI.
  • Delta para tudo: TimeTravel cobre auditoria; Change Data Feed habilitado nas tabelas mutáveis facilita observabilidade.
  • Modelo editorial via ticket: nenhuma mutation grava direto. Vai pra ticket OPEN MANUAL (janela 15 min) → apply em lote. Decisão crítica — viabiliza governança e undo de sessão.

Padrão arquitetural

Arquitetura em camadas modulares por feature. Cada módulo de domínio (M1-M11) é um pacote Python com router → service → models + pacote TypeScript equivalente em ui/routes + ui/components. Convenções rigorosas:

  • Models 3-tier: EntityIn (request), EntityOut (response), tabela Delta correspondente.
  • DI via Dependencies class: .Client (SP app), .UserClient (OBO), .Config, .Sql.
  • SQL via DAO parametrizado: nunca f-string com input externo. Sempre delta.param("nome", valor).
  • Editorial model: mutations → session.stage_entity_change() → ticket OPEN → apply_ticket().
  • Migrations versionadas com checksum: registradas em schema_migrations. Drift detection só loga warning.

5. Funcionalidades Principais (Deep Dive)

5.1 Engenharia Reversa Multi-Fonte (M2)

O que faz: extrai modelo de fonte externa e gera snapshot estruturado pra reconciliar com o catálogo.

Componentes chave:

  • backend/extractions/service.py — orquestra 4 entradas: extract_from_lakebase, extract_from_uc, run_ddl_import, run_embarcadero_import
  • backend/extractions/embarcadero.py — parser .DM1 ASCII multi-seção do ER/Studio
  • backend/extractions/models.py — ExtractionSnapshot, ExtractedEntity/Attribute/Index/IndexColumn

Regras críticas (não quebrar):

  • DM1 duplicação lógico/físico: ER/Studio armazena cada entity 2x (ModelId=1 e ModelId=2). Dedup por (schema, technical_name) mantendo a versão física.
  • Cap de upload 50 MB (EmbarcaderoImportIn.dm1_text). Não aumentar sem entender DoS no parser.
  • Lakebase OAuth M2M: app_ws (SP) chama database.generate_database_credential. user_ws (OBO) não tem scope postgres.
  • Indexes só não-PK (NOT i.indisprimary). PK vai via is_primary_key=true no attribute.

5.2 Modelo Editorial via Tickets (M5)

O que faz: toda mutation passa por ticket OPEN MANUAL com janela de 15 min — user edita várias entities/attributes/indexes/partition, revisa e aplica em lote. Materialização atômica.

Componentes chave:

  • backend/tickets/service.py — apply_ticket (≈700 linhas, máquina de estados grande)
  • backend/tickets/session.py — find_open_session_ticket, stage_entity_change
  • backend/tickets/models.py — DiffEntity (com attributes + indexes + field_changes)

Regras críticas:

  • pre_allocated_entity_id deve ser preservado no apply. Sem isso, relationships virtuais ficam órfãos.
  • Field changes prefixados (apply roteia por prefixo): attribute_add:, attribute_remove:, attribute:NAME.update, index_add:, index_remove:, index_change:, partitioning:set. Novos prefixos exigem match no apply_ticket.
  • _quote_lit escapa backslash antes de aspas (linha 48-72 de delta.py). Bug histórico: JSON com \" ficava corrompido.
  • /apply ≠ /reopen: 2 decorators @router.post empilhados na mesma função zeram a rota. Sempre cada decorator em sua função.

5.3 Índices & Particionamento (F1-F9)

O que faz: catálogo + governança editorial + DDL generation + overlay no DER pra índices e particionamento por entity.

Componentes chave:

  • databricks/sql/012_indexes_and_partitioning.sql — schema das tabelas
  • backend/entities/indexes.py + index_overlay.py + index_validation.py
  • backend/ddl/generators.py — _render_indexes_postgres/oracle/tsql/mysql + _partition_clause_*
  • ui/components/diagram/{indexes,partitioning}-section.tsx · index-types-by-tech.ts · entity-node.tsx

Regras críticas:

  • origin='EXTRACTED' vs 'MANUAL' — preservar pra futura sync round-trip.
  • columns em entity_indexes é JSON string (não ARRAY<STRUCT>) — Statement Execution API tem fricção com struct arrays.
  • Liquid clustering Delta → emitido como ALTER TABLE ... CLUSTER BY fora do CREATE.
  • Partition em coluna nullable → warning (PG/Oracle exigem NOT NULL).

5.4 DDL Multi-Dialeto (M10)

O que faz: gera DDL portável a partir do catálogo, em 6 dialetos (ANSI, T-SQL, PL/SQL, PostgreSQL, MySQL, Spark/Delta).

Componentes chave:

  • backend/ddl/generators.py — gen_ansi/tsql/plsql/postgres/mysql/sparksql + map_type
  • backend/ddl/service.py — fetch_entities_with_attrs + fetch_indexes_and_partitioning

Regras críticas:

  • Generator é função pura — recebe entity, attrs, opts, retorna string. Não acessa DB. Facilita golden tests.
  • map_type heurística — tipos desconhecidos viram VARCHAR(255). Mudança aqui aciona 61 testes de regressão.

5.5 Diagrama Entidade-Relacionamento (M4)

O que faz: render visual do modelo com drag-and-drop, overlay editorial, badges de índices/partição, edição inline.

Componentes chave:

  • ui/routes/_sidebar/diagram.tsx — página container (XYFlow + Dagre)
  • ui/components/diagram/entity-node.tsx — custom node
  • backend/diagram/router.py — GET /api/diagram com overlay de ticket OPEN

Regras críticas:

  • Overlay no backend (_apply_session_overlay). Entities virtuais (op=add) recebem entity_id virtual; FK overlay usa pre_allocated_entity_id.
  • is_indexed calculado por loop no _build_diagram — se DER lento com 1000+ atributos, otimizar aqui.
  • Layout salvo em der_layouts (migration 007). Fallback p/ dagre auto.

5.6 RBAC + Auditoria

O que faz: 4 papéis (VIEWER · STEWARD · ARCHITECT · ADMIN) + audit log imutável.

Componentes chave:

  • backend/rbac/router.py — require_role()
  • backend/audit/middleware.py — grava request/response em audit_log
  • Migration 005_tickets_and_roles.sql — tabela user_roles

Regras críticas:

  • Decisão por ação, não por endpoint: apply_ticket exige ADMIN; publish_version exige ARCHITECT+ADMIN.
  • Audit é Delta TimeTravel-friendly — só INSERT, nunca UPDATE/DELETE.
  • Primeiro user precisa seed manual de ADMIN em user_roles.

6. Pontos de Atenção e Débito Técnico

Hotspots de complexidade

ArquivoLinhasRiscoMitigação
backend/tickets/service.py ~759 apply_ticket parsing + roteamento por prefixo + apply em 5 tabelas. Mudança pode quebrar attribute/index/partition em cascata. Cobrir cada caminho com test. Quebrar em sub-handlers por prefixo.

Limitações estruturais conhecidas

  • Statement Execution API sem array params — queries com WHERE id IN (...) usam _quote_id() manual. Trust pela origem (id veio de SELECT prévio do app).
  • DM1 datatype map é calibrado por amostra — IDs desconhecidos viram heurística. Calibrar com novos exports do cliente.
  • Liquid clustering: assume properties['clusteringColumns'] em JSON. Formato UC pode mudar.
  • Coverage gate em 65% (pyproject.toml). Subir gradual.
  • Drift de migrations só loga — em rollback de versão pode ficar inconsistente.

Bugs históricos pra não repetir

  • /apply colidindo com /reopen: 2 decorators na mesma função → Python sobrescreve. Sempre 1 decorator por função.
  • JSON com \" corrompido: _quote_lit precisava escapar backslash antes de aspas.
  • FK entre entities virtuais retornava 400: overlay usava pending-ent-public.X ao invés de pre_allocated_entity_id.

Próximos passos sugeridos

  1. Subir coverage gate p/ 75-80%. Gaps conhecidos: tickets/service.py:_apply_relationship_change, extractions/service.py:run_uc_extraction.
  2. Refatorar apply_ticket em sub-handlers por prefixo.
  3. Round-trip Lakebase: mudanças no app viram ALTER TABLE no Postgres real (hoje só read).
  4. E2E coverage: hoje só smoke + indexes. Adicionar tickets approval + DDL export.
  5. Manter scripts.dump_openapi após qualquer mudança de signature (CI tem drift check).

7.2 Export do código do workspace origem

O código já está sincronizado num caminho do tipo /Workspace/Users/<seu-usuário>/nuclea-modeler no workspace origem. Pra exportá-lo:

  1. Acesse o workspace origem

    Faça login no workspace Databricks onde o app está rodando hoje.

  2. Abra o Workspace Browser

    Menu lateral: Workspace
    Navegue até a pasta do código: Users › <email@origem> › nuclea-modeler.

  3. Exporte como arquivo

    Clique no menu de três pontinhos ao lado do nome da pasta nuclea-modeler.
    Selecione Export › Source File (.zip) (ou DBC, mas .zip preserva estrutura de arquivos texto e é mais portável).
    O browser baixa um nuclea-modeler.zip contendo todo o source: src/, databricks/sql/, app.yml, pyproject.toml, package.json, requirements.txt, scripts/, docs/ e tests.
    Por que .zip DBC empacota notebooks e perde arquivos não-notebook (.py puros sem cell markers, .ts, .json). O Source File (.zip) preserva bytes exatamente.

  4. (Opcional) Exporte o estado atual do catálogo

    Se quiser migrar também os dados (não só o código), abra o SQL Editor e rode no workspace origem:
    -- Substitua pelos seus valores
CREATE TABLE <DESTINO_CATALOG>.<DESTINO_SCHEMA>.systems
  DEEP CLONE <ORIGEM_CATALOG>.<ORIGEM_SCHEMA>.systems;
-- Repita para cada uma das 22 tabelas (lista completa na seção 7.6)
    Alternativa mais simples se os workspaces compartilham metastore: Delta Sharing via Catalog UI.
    Se você só quer recomeçar limpo no destino (cliente novo, modelo zerado), pule este passo — as migrations criam tudo vazio.

7.3 Import no workspace destino

  1. Faça login no workspace destino

    URL diferente do origem. Use a conta com permissão de admin/can-manage-apps.

  2. Crie pasta do app na sua home

    Workspace › Users › <seu-email> — três pontinhos Create › Folder — nome: nuclea-modeler.

  3. Importe o .zip

    Entre na pasta nuclea-modeler que acabou de criar.
    Três pontinhos Import. Selecione o nuclea-modeler.zip baixado no passo 7.2.3.
    No diálogo, escolha "Source files". Confirme.
    A UI mostra um spinner; alguns segundos depois a pasta vai conter toda a árvore: src/, databricks/sql/, app.yml, pyproject.toml, etc.
    Limite de tamanho Workspace Import aceita até ~10MB por upload de zip. O repo descompactado tem ~5MB. Se exceder, exporte por subpastas (ex: src.zip separado de databricks.zip) e importe sequencialmente.

  4. Confirme a estrutura

    Navegue dentro da pasta importada e verifique que existem:
    • app.yml (vai editar nos próximos passos)
    • app.yml.example (template de referência)
    • requirements.txt
    • pyproject.toml

7.4 Configuração do app — editar app.yml pela UI

  1. Abra app.yml no editor da Workspace

    No Workspace Browser, dê duplo-clique em app.yml. Ele abre num editor de texto inline (sem precisar baixar/editar local).
    Dica Se preferir um template do zero: copie tudo de app.yml.example e cole sobrescrevendo app.yml. O .example tem os placeholders <ALTERAR> explícitos.

  2. Anote os valores que vai usar

    Abra outra aba do navegador no workspace destino e colete:

    ValorOnde achar na UI
    Warehouse ID SQL › SQL Warehouses — clique no seu warehouse — copie o trecho final da URL /sql/warehouses/abc123def
    Catalog name Catalog — navegue até o catalog escolhido — o nome aparece no topo (ex: main, nuclea_prod)
    Lakebase instance name (opcional) Compute › Lakebase — clique na instance — copie o "Instance name" (ex: JDBCTESTLAKEBASE)

  3. Edite app.yml substituindo os placeholders

    No editor inline, troque os 4 placeholders. Exemplo do estado final:
    resources:
  - name: nuclea-warehouse
    sql_warehouse:
      id: "abc123def"                ## ← seu Warehouse ID
      permission: CAN_USE

  - name: nuclea-lakebase             ## remova este bloco inteiro se não usar Lakebase
    database:
      database_name: "databricks_postgres"
      instance_name: "JDBCTESTLAKEBASE"  ## ← seu Lakebase
      permission: CAN_CONNECT_AND_CREATE

env:
  - name: NUCLEA_CATALOG
    value: "main"                    ## ← seu catalog
  - name: NUCLEA_SCHEMA
    value: "nuclea_modeler"          ## deixa este, é criado automaticamente
  - name: NUCLEA_WAREHOUSE_ID
    value: "abc123def"               ## ← mesmo Warehouse ID
  - name: DATABRICKS_SQL_WAREHOUSE_ID
    value: "abc123def"               ## ← mesmo

  4. Salve com Ctrl+S (ou ⌘+S)

    O editor do Workspace persiste imediatamente. Sem commit, sem push.

7.5 Criar o app + grants pelo Catalog Explorer

  1. Crie o app pela UI de Apps

    Menu lateral Compute › Apps — botão Create app no canto superior direito.
    Nome: nuclea-modeler. Descrição livre. Clique Create.
    Na tela do app criado, vá na aba "Service Principal" e copie o Application ID (UUID). Você vai usar nos grants do passo seguinte.

  2. Conceda permissões ao SP do app via Catalog UI

    Vá em Catalog — clique no catalog escolhido (ex: main).
    Aba Permissions — botão Grant.
    No campo Principals: cole o Application ID do SP do app que você copiou (UUID).
    Marque os checkboxes:
    • USE_CATALOG
    • USE_SCHEMA (se já existir um schema padrão)
    • CREATE_SCHEMA
    • CREATE_TABLE
    • MODIFY
    • SELECT
    Confirme com Grant.
    Atalho via SQL Editor Equivalente pela UI do SQL Editor (cole no editor e Run): 
    GRANT USE CATALOG, CREATE SCHEMA ON CATALOG <catalog_name>
  TO `<application_id>`;

  3. (Se usar Lakebase) Grant no Lakebase

    Compute › Lakebase — clique na instance — aba Permissions.
    Adicione o Application ID do SP com permissão Can Connect and Create.

7.6 Deploy & verificação pela UI

  1. Configure o source-code-path no app

    Volte em Compute › Apps › nuclea-modeler.
    Aba Settings (ou "App configuration") — campo Source code path.
    Cole o caminho onde você importou: /Workspace/Users/<seu-email>/nuclea-modeler.
    Salve.

  2. Dispare o deploy

    Na tela do app, botão Deploy (canto superior direito).
    A UI mostra o status: Provisioning → Starting → Running. Demora ~1-2 min.
    Durante o deploy o container roda:
    1. vite build — gera o bundle React em src/nuclea_modeler/__dist__/
    2. python -m scripts.run_migrations — aplica as 12 migrations SQL em ordem
    3. uvicorn nuclea_modeler.backend.app:app — sobe o servidor FastAPI (2 workers)

  3. Verifique os logs pela UI

    Aba Logs do app. Procure por:
    • [NUCLEA] Building UI...
    • [NUCLEA] Running migrations
    • summary: {'applied': N, 'skipped': M, ...} — N migrations aplicadas (12 no deploy limpo)
    • Application startup complete — uvicorn pronto
    Se aparecer erro de SCHEMA_NOT_FOUND Volte ao passo 7.5.2 e confirme que o grant CREATE_SCHEMA foi aplicado ao Application ID correto. O Application ID está na aba Service Principal do app.
    Se aparecer "Provided OAuth token does not have required scopes: postgres" O bloco nuclea-lakebase em resources: do app.yml não foi declarado ou tem placeholder. Edite o YAML pela UI (passo 7.4) e re-deploy.

  4. Verifique que as tabelas foram criadas

    Vá em Catalog › <catalog_name> › nuclea_modeler.
    Você deve ver as 22 tabelas Delta:
    DomínioTabelas
    M1 Sistemas + Conexõessystems · connections
    M3 Modelagementities · attributes · relationships
    M5 Workflowreconciliation_tickets · user_roles
    M2 Extractionsextractions
    M4 DERder_layouts
    M6 Flagsflags · entity_flags · attribute_flags
    M7 Glossárioglossary_terms · glossary_mappings
    M8 Linhagemlineage_upstream · lineage_downstream
    M9/M11 Operacionalsync_log · audit_log · model_versions · views_catalog · procedures_catalog · triggers_catalog
    F1-F9 Storageentity_indexes · entity_partitioning
    Internoschema_migrations · sequences

  5. Acesse o app

    Na tela do app, copie a URL pública (formato https://nuclea-modeler-<workspace_id>.cloud.databricksapps.com).
    Abra num nova aba. SSO força login automático.

  6. Bootstrap do primeiro admin

    O primeiro user a entrar fica como VIEWER. Pra dar role ADMIN via UI:
    SQL › SQL Editor — cole e Run:
    INSERT INTO <catalog_name>.nuclea_modeler.user_roles
  (role_id, user_email, role_name, granted_at, granted_by)
VALUES (uuid(), 'seu-email@cliente.com', 'ADMIN',
        current_timestamp(), 'bootstrap');
    Recarregue o app — agora você tem acesso completo.

  7. (Opcional) Dashboard Lakeview + Genie

    Workspace › Users › <seu-email> › nuclea-modeler › databricks › dashboards.
    Clique em nuclea_modeler_dashboard.json, três pontinhos Open in dashboard editor.
    A UI vai pedir pra substituir o catalog/schema — aponte para o seu (<catalog>.nuclea_modeler) e salve.
    Genie: SQL › Genie Spaces › Create new space — siga databricks/dashboards/GENIE_SETUP.md (instruções de UI passo-a-passo).

7.7 Atualizações (re-deploy de nova versão)

Quando publicarmos uma nova versão (cliente recebe novo .zip nosso):

  1. Re-import sobrescrevendo

    Workspace › nuclea-modeler — três pontinhos Import — selecione o zip novo. Aceite "overwrite existing files".
    Cuidado O Import sobrescreve incluindo app.yml. Se você editou o YAML manualmente no passo 7.4, salve uma cópia em outra pasta antes do import — ou faça o backup baixando o app.yml atual via three-dots Export antes.

  2. Re-edite app.yml se necessário

    Confirme que os placeholders ainda estão substituídos (passo 7.4) — se o overwrite trouxe o template do .example, reaplique seus valores.

  3. Re-deploy pelo botão

    No app: Deploy. Migrations novas (ex: 013_*.sql) aplicam automaticamente; migrations existentes ficam como skipped via checksum.

7.8 Troubleshooting (sintomas → fix pela UI)

Sintoma nos LogsCausaFix via UI
SCHEMA_NOT_FOUND SP do app sem CREATE SCHEMA no catalog Volte ao 7.5.2 — Catalog UI → Permissions → Grant CREATE_SCHEMA pro Application ID
required scopes: postgres Bloco nuclea-lakebase não declarado em resources: Edite app.yml pela UI (7.4) + Deploy de novo
DRIFT detected: 0XX_*.sql SQL já aplicado teve hash mudado Normal em upgrades — app continua subindo. Investigue só se for migration sua, não nossa
DER vazio / Dashboard sem dados Seeds (003-004-009) falharam Logs do app — procure stack trace nas migrations. Geralmente é grant ou catalog inválido
401 em todos os endpoints SSO força auth, browser sem cookie Abra a URL do app na mesma sessão em que está logado no workspace
App fica em "Starting" pra sempre Container OOM (UI build pesado) ou ECONNREFUSED Logs do app — se viu OOM, aumente memory na config do app (Settings → Resource size)
Bundle UI antigo após deploy Browser cache Hard refresh: ⌘+Shift+R (ou Ctrl+Shift+R)
Coverage gate falhando em CI (não bloqueia deploy) Ajuste de testes pendente Não afeta o app rodando. Tem que ajustar cov-fail-under em pyproject.toml pela UI
Pronto Se chegou aqui com logs verdes e UI acessível, o handover está concluído. Estado migrado, app rodando independente do workspace origem.
